# Lido core threat model

This file describes `lidofinance/core` for an offline security review. The security goal of the protocol has two parts. Every stETH share is backed: internal shares by ETH that Lido holds in its contracts or has staked under Lido withdrawal credentials, external shares by the assets of the connected stVault, which stakes under its own credentials. ETH leaves the protocol only to the party entitled to it. The priorities in section 2 and the severity rubric in section 7 follow that goal.

## 1. What Lido core is and where untrusted input enters

- `Lido` issues stETH, a rebasing ERC-20 over shares: balance = `shares × internalEther / internalShares`. `WstETH` wraps shares (1 wstETH = 1 share). Accounting is balance-based (LIP-35): `internalEther` = buffered ETH + reported validator balance + reported pending-deposit balance + ETH deposited since the last oracle report.
- Deposits: `StakingRouter` sends buffered ETH to module validators. A 32 ETH seed deposit needs a guardian quorum in `DepositSecurityModule` (DSM). `TopUpGateway` tops up `0x02` validators. `ConsolidationMigrator`, `ConsolidationBus` and `ConsolidationGateway` consolidate validators.
- Oracle report: the committee agrees on one report per frame in `HashConsensus`, `AccountingOracle` submits it, and `Accounting` applies it in one transaction (rebase, fees, burns, withdrawal finalization).
- Withdrawals and exits: `WithdrawalQueueERC721`, `ValidatorsExitBus(Oracle)` (VEB, VEBO), `TriggerableWithdrawalsGateway` (TWG), `WithdrawalVault`, `ValidatorExitDelayVerifier`.
- stVaults: a vault owner stakes ETH in a `StakingVault` and mints stETH as external shares through `VaultHub`. `LazyOracle` applies vault reports. `PredepositGuarantee` (PDG) guards vault deposits with EIP-4788 proofs and node-operator bonds.

Untrusted input enters in three ways. Every permissionless call (section 3). Consensus-layer state, which reaches core through the oracle committee's reports and through proofs against the EIP-4788 root. External code that core calls: ERC-1271 guardian contracts, staking modules and rebase observers. Easy Track works the other way round: it is a privileged external caller that core checks only for a role (section 3).

Names: core tags are `vX.Y.Z`. Release names are Lido V2 (audited 2023), Lido V3 (stVaults, audited 2025) and Staking Router v3 (LIP-35, core `v4.0.0`, audited 2026). `StakingRouter` contract version 4 and DSM `VERSION = 5` are contract versions. "Oracle report" is the `AccountingOracle` report and "vault report" is a `LazyOracle` leaf update.

### Deployment status

Four states describe how a piece of code relates to mainnet:

- **Live**: deployed on mainnet and reachable with the deployed constructor arguments.
- **Live, unused path**: deployed code that the deployment cannot reach. Example: the fork-pivot branches of the CL proof verifiers while their previous and current generalized-index constructor arguments in `/src/deployed-mainnet.json` are equal (true at `v4.1.0`). If the values differ, the pivot branch is live.
- **Future upgrade**: code that runs only after a redeploy or migration. Example: a new `OracleReportSanityChecker` and its permissionless one-shot `migrateBaselineSnapshot()`. The `v4.0.0` upgrade already called it on the live checker.
- **Not deployed / retired**: the four EDF fixtures under `contracts/upgrade/` (NatSpec: testnets and local forks only), the executed `v4.0.0` upgrade template, and retired DSM and sanity-checker addresses. Out of scope unless a live contract still trusts or pays them.

## 3. Actors and trust boundaries

### Untrusted: an attacker may do all of this

- Use any number of EOAs and contracts, flash loans, and transaction ordering inside a block.
- Submit, transfer, approve, permit, wrap, unwrap, request withdrawals (100 wei to 1000 stETH each), claim own requests to any recipient, and force ETH into any contract.
- Deposit to the beacon deposit contract for any pubkey and withdrawal credentials, including Lido keys and vault credentials. Run own validators, send EIP-7002 requests for them, and consolidate them into any `0x02` validator, including Lido and vault validators. The consensus layer does not require the source and target to share an owner. It requires an active target with compounding credentials and no initiated exit, and a source with matching execution credentials, active for `SHARD_COMMITTEE_PERIOD`, with no pending withdrawals.
- Relay guardian-signed DSM messages, execute matured consolidation batches, reveal committed exit data, call `ValidatorsExitBus.triggerExits` on delivered data with the fee, submit exit-delay proofs, and pick any refund recipient.
- Act as a node operator with its own keys. Create vaults through `VaultFactory`, and own, operate, deposit for or guarantee them. Call the permissionless PDG proof and activation functions, push any vault leaf with a valid Merkle proof, and call `forceRebalance`, `settleLidoFees`, `NodeOperatorFee.disburseFee` and `Burner.recoverExcessStETH`.

The off-chain oracle reports consensus-layer state that attackers can shape with these actions. On-chain checks (sanity checker, quarantine, PDG stages) are what bounds the effect on `totalValue`, pending balance or minting capacity, so a CL action that gets past one of them is in scope.

### Fully trusted

- The Aragon Agent behind Dual Governance (LIP-28): proxy admin and `DEFAULT_ADMIN_ROLE` holder of the core contracts (the `v4.0.0` upgrade template asserts this), manager of the `Lido` Aragon roles, owner of the `StakingVault` beacon. The DSM owner sets guardians and unpauses deposits. No code bound.
- The consensus layer, the EIP-4788 beacon-roots contract, the EIP-7002 and EIP-7251 predeploys, and the deposit contract behave as specified. The consensus layer ignores an EIP-7002 request whose source is not the validator's withdrawal address.
- Rebase observers that the `TokenRateNotifier` owner registers (at most 32).

An attack that needs a bounded or trusted actor is a finding where that actor gets past a bound the code should enforce.

## 4. Invariants to test

The IDs in brackets name the source of a property. `P-AC`, `P-BU`, `P-LI`, `P-VH`, `P-LO`, `P-PG` and `P-OG` are properties from the Certora formal verification of Lido V3, and `F-*` are its fuzz suites. `P-ALLOC`, `P-DEPOSIT`, `P-TOPUP`, `P-ACCOUNT`, `P-RESERVE`, `P-ADDRESS`, `P-SSZ`, `P-CONSOLIDATION` and `P-ORACLE-SUPPLY` come from the Staking Router v3 proof-closure model by LFG Labs, pinned to core `v4.0.0`. Properties without an ID are guards read from the `v4.1.0` code. The proofs are conditional models, so a violation in the code is still a finding.

Backing:

1. `Lido.getBufferedEther()` never exceeds the `Lido` contract's ETH balance (P-LI-01). `internalEther` counts only buffered ETH, reported CL balances, the reported pending-deposit balance and ETH deposited since the last oracle report. `Lido.getExternalShares()` equals the sum of connected vaults' `liabilityShares` plus `VaultHub.badDebtToInternalize()` (P-LI-02), and a disconnected vault has zero `liabilityShares` and zero `locked` (P-VH-02).
2. No transaction outside `Accounting.handleOracleReport` lowers `internalEther / internalShares`. `submit`, external mint and burn, and `rebalanceExternalEtherToInternal` keep the rate equal or higher. No vault path lowers the share rate except `Lido.internalizeExternalBadDebt` in the oracle report.
3. Apart from `submit` and the `VaultHub` external-share calls, only `Accounting` during an oracle report, and `Burner.commitSharesToBurn` (callable only by `Accounting`), change share supply or change `internalEther` by a non-user amount. Shares sent to the `Burner` are only burned, never transferred out, except through `recoverExcessStETH` (P-BU-01).
4. `Σ shares == totalShares`, `externalShares ≤ totalShares`, `internalShares > 0`. `wstETH` holds at least as many shares as its total supply.

Oracle report:

5. Each deposit enters exactly one oracle report's principal through `depositedPostReport` and `depositedNextReport`, and `depositedNextReport ≤ depositedPostReport` always holds: `getBalanceStats()` subtracts them unchecked in Solidity 0.4.24.
6. Every oracle report passes the sanity checks. Per-module balances sum exactly to the reported CL total, with no tolerance. The report lists every registered module in registration order. The pending balance grows at most by deposits plus `externalPendingBalanceCapEth`. The activated balance stays within the daily allowance plus one 2048 ETH validator. The withdrawal vault balance is at least its stored post-transfer value. The 36-day decrease-window baseline cannot be reset by skipping reports. The annual increase limit holds. When the report finalizes, the simulated share-rate check passes.
7. No fee shares are minted when the CL side, including the withdrawal-vault transfer, did not grow (LIP-12). Minted fee shares are the designated fraction of the growth (P-AC-01) and are bounded by `feeEther × internalShares / (postInternalEther − feeEther)` (P-ORACLE-SUPPLY-1). Within one report, the router balance write precedes the rewards-distribution read, which precedes any fee mint (P-ACCOUNT-1). A revert anywhere undoes the whole oracle report.
8. The buffer is allocated in order. The deposits reserve comes first: deposits consume it, an oracle report raises it back to its target in `_updateBufferedEtherAllocation`, and only a lower target lowers it immediately. The withdrawals reserve comes second, `min(remaining, unfinalizedStETH)`, and is not depositable. The unreserved rest comes last. Depositable ETH is `depositsReserve + unreserved`: a deposit or top-up never spends the withdrawals reserve (P-RESERVE-1), and the deposits reserve is outside the read set of finalization (P-RESERVE-RELATIONAL).

Deposits, top-ups and consolidations:

9. Only `LidoLocator.depositSecurityModule()` calls `StakingRouter.deposit`, and only `LidoLocator.topUpGateway()` calls `StakingRouter.topUp`. Deposit ETH leaves `Lido` only through `withdrawDepositableEther`, which needs `canDeposit()` (not stopped, no bunker mode) and the router as caller.
10. Across `deposit` and `topUp` the router balance is unchanged (asserted before and after), and its `receive()` rejects plain transfers. Every pulled wei goes to the deposit contract with Lido withdrawal credentials in the same call, and a failure rolls the whole call back (P-DEPOSIT-1, P-TOPUP-1).
11. Every top-up target is proven active with the module's `0x02` credentials against an EIP-4788 root younger than `maxRootAge`; a missing or overwritten root fails closed (P-SSZ-LIVE-1). An exiting or slashed target gets a zero limit. A zero allocation is skipped; every non-zero amount is gwei-aligned, at least 1 ETH and within the gateway limit, and the exact sum of allocations stays within the router cap and `maxTopUpPerBlockGwei` (P-TOPUP-2).
12. Every consolidation target is proven to carry `0x02` credentials for `LidoLocator.withdrawalVault()`. A batch executes only after the bus delay, while DSM deposits are not paused and `Lido.canDeposit()` is true. The gateway forwards exactly `requestsCount × fee` to the EIP-7251 predeploy through `WithdrawalVault`, refunds the excess of `msg.value` to the refund recipient, and restores the entry state on failure (P-CONSOLIDATION-1, P-CONSOLIDATION-VALUE-1). The migrator publishes only pubkeys read from its fixed source and target modules, at indices below each operator's deposited count, and only for the registered submitter of that pair.
13. An Active module gets at most its share cap of the post-deposit total, and the MinFirst allocation conserves the request and respects demand and capacity (P-ALLOC-1, P-ALLOC-2). All modules have the same `moduleFee + treasuryFee`. Deposited validator counts never decrease (P-LI-05). On the oracle path (`updateExitedValidatorsCountByStakingModule`), exited counts never decrease and never exceed deposited counts. `unsafeSetExitedValidatorsCount` (`UNSAFE_SET_EXITED_VALIDATORS_ROLE`) can lower them by design but cannot exceed deposited counts.

Withdrawals and exits:

14. A claim pays `min(requested stETH, shares × R / 1e27)`, where `R` is the rate of the checkpoint that contains the request. Only the owner claims, once. The chosen recipient changes only the destination of the ETH, never the amount or the queue state (P-ADDRESS-1).
15. Finalization is contiguous. One `finalize` locks at most the stETH of its range, and claims never exceed what it locked. `lockedEtherAmount` never underflows or exceeds the queue balance.
16. `WithdrawalVault` loses ETH only through `withdrawWithdrawals`, called by `Lido` in an oracle report. Only the two immutable gateways make exit or consolidation requests, each spending exactly `msg.value`.
17. Exit data is triggerable only after delivery. Each trigger pays the full EIP-7002 fee and consumes the gateway limit when one is set.
18. The exit-bus decoders read the same module, operator, key and pubkey for each item. On the oracle path each pubkey equals the module key at `(nodeOperatorId, keyIndex)`.
19. A delay proof needs a header matching the EIP-4788 root, a validator at the requested index with the requested pubkey and no exit epoch, and a proof slot after both delivery and activation plus `SHARD_COMMITTEE_PERIOD`.

stVaults:

20. `mintShares` needs a fresh vault report, an unjailed vault, `locked ≤ totalValue − unsettledLidoFees`, the vault, tier and group limits, `maxExternalRatioBP` and the staking limit. A withdrawal never leaves `totalValue` below `locked` plus unsettled Lido fees. `maxLiabilityShares ≥ liabilityShares` and `redemptionShares ≤ liabilityShares` (P-VH-04); `redemptionShares` rises only through `setLiabilitySharesTarget` under `REDEMPTION_MASTER_ROLE` (P-VH-05).
21. A healthy vault stays healthy through any sequence of user operations until the next oracle report (P-VH-06, F-02), with two known exceptions: `settleLidoFees`, and the rounding of repeated small owner rebalances (Certora V3, L-19, section 6). `locked` covers liabilities plus the reserve across share-rate changes, tier updates, rebalancing and fee settlement (F-01), and rebalancing by `healthShortfallShares()` restores health (F-03). Tier and vault reserve ratios stay within `TOTAL_BASIS_POINTS` and above the forced-rebalance thresholds (P-VH-03).
22. A `totalValue` increase above the `maxRewardRatioBP` threshold does not count before the quarantine period ends, a quarantine cannot be reused after expiry, and funds release only at its end (P-LO-02). A vault leaf applies at most once per root.
23. A PDG predeposit sends exactly 1 ETH per validator before any proof and locks 1 ETH of the node operator's bond for it. The staged 31 ETH activation, and every later PDG deposit, go only to validators proven to carry the vault's credentials. Each pubkey moves through the PDG stage machine once, in order (P-PG-01). At connect, the vault is factory-deployed, not ossified, has PDG as depositor and has `stagedBalance == 31 ETH × pendingActivations`. While the vault is connected, PDG keeps 31 ETH staged for each predeposited validator that is not yet activated.
24. Per node operator, PDG `locked ≤ total` and `locked == 1 ETH × predeposited validators`. The PDG ETH balance covers all bonds plus guarantor refunds.
25. Each tier's `liabilityShares` equals the sum over its vaults, and each group's equals the sum over its non-default tiers. The vaults array holds no duplicates (P-VH-01).

Cross-cutting:

26. Proxy upgrades need the proxy admin. Implementations cannot be initialized. Each `initialize` and `finalizeUpgrade_vN` runs once, from the expected prior version. A `whenResumed` path reverts while paused.
27. A module registered with `0x02` credentials must implement `IStakingModuleV2`: the router calls `getTotalModuleStake()` in every allocation pass and `allocateDeposits()` in `topUp`, so a type-2 module without them halts every deposit and top-up.

## 5. High-yield areas

- **Proofs.** `TopUpGateway` (full `Validator` container), `ConsolidationGateway` and PDG (pubkey and credentials through `CLProofVerifier`), and `ValidatorExitDelayVerifier` (including `historical_summaries`). The subtle parts are gindex concatenation, slot binding, proof length, little-endian fields and `PIVOT_SLOT` selection. Only `TopUpGateway` bounds root age. The others accept any root still in the EIP-4788 ring buffer. PDG checks each predeposit's BLS signature with the EIP-2537 precompiles: the y-coordinate and length inputs, the deposit domain, and acceptance of a signature for another pubkey, amount or withdrawal credentials are the places to look.
- **Key-to-owner binding.** The gateways prove credentials, not module or operator ownership, and all type-2 modules share one `0x02` credentials word. Exit format 2 proves pubkey-to-key-index registration, not deposit status or `validatorIndex`. A permissionless way to exit, penalize or fund a validator under the wrong module or operator would be a finding.
- **Two credential sources.** Deposits and top-up proofs use the word stored in `StakingRouter`. Consolidation proofs derive it from `LidoLocator.withdrawalVault()`.
- **LIP-35 accounting.** Deposit-frame bucketing and 128-bit packed slots in `Lido.sol` (Solidity 0.4.24), and values carried from simulation to application in `Accounting.sol`. The vault code predates the `v4.0.0` `_getInternalEther` formula that every vault conversion uses.
- **Sanity-checker CL bounds**, rewritten during the 2026 Staking Router v3 audits: moves between pending and validator balance, the two increase checks, the 36-day window baseline, and modules without a stored baseline.
- **Extra data.** `AccountingOracle` parses item headers in assembly, checks index order and sorting, chains chunk hashes, has an empty path, sends counts to module hooks, and has a processing deadline.
- **Bad-debt pipeline**: `VaultHub.internalizeBadDebt`, then `RefSlotCache`, then `Accounting`, then `Lido.internalizeExternalBadDebt`. A mismatch can revert the oracle report or misprice the rebase.
- **stVault clusters.** The 2025 Lido V3 audits (Certora V3, Consensys V3) found fixed Critical or High issues in each of these clusters:
  - LazyOracle quarantine, `DoubleRefSlotCache` lookups, freshness, gifts with `fund` or `withdraw`, and connect or disconnect around a ref slot.
  - The PDG stage machine, bonds, compensation routing and cross-vault predeposits.
  - Obligations and `redemptionShares`.
  - `locked` after tier and connection updates.
  - Lido and node-operator fee settlement, including fees above `totalValue`.
- **Callbacks and caller-chosen recipients**: claims, fee refunds (TWG, `ConsolidationGateway`, `ValidatorsExitBus.triggerExits`), PDG ETH sends and `depositFromStaged` calls into vault code, and unstETH `onERC721Received`. The questions are whether state is written before each call, whether `preservesEthBalance` holds under re-entry, and what re-entry into another protocol entry point in the same transaction can do.
- **External code inside the oracle report.** Module hooks and rebase observers get the remaining gas. A permissionless way to make them revert with empty data, or re-entry into `Lido` during the oracle report, would be a finding.
- **DSM v5 signatures.** OpenZeppelin 4.4 `SignatureChecker` tries ECDSA recovery, then ERC-1271. Sorting uses the claimed `guardian` field. Replay across seats, message types, modules, DSM instances and chains is the question.
- **Branches that move no ETH.** A top-up with all-zero allocations and a zero-key seed deposit still call modules and change state, and skip some guards.
- **Finalization math**: batch amounts in `prefinalize` against per-request amounts at claim, `_findCheckpointHint` boundaries, and tiny requests near `maxShareRate`.
- **Cached addresses.** Some contracts read `LidoLocator` per call, others cache immutables (`WithdrawalVault` gateways, the consolidation stack). A stale address that can still authorize or receive value would be a finding.
- **Dual Governance coupling.** The escrow at `/opt/lido/dual-governance/contracts/Escrow.sol` converts stETH through `getSharesByPooledEth` and `getPooledEthByShares`, and uses `requestWithdrawals`, `getWithdrawalStatus`, `getClaimableEther` and `claimWithdrawals` for rage-quit support. A core bug that shifts this weight or blocks escrow withdrawals affects governance.

## 6. Known and accepted behaviour

Each item below names a known mechanism with its known consequence. The mechanism as described is not news. A variant that gets past a bound in a new way, needs a new precondition, or reaches a larger impact is a finding; the "still report if" notes are examples of such variants, not an exhaustive list.

Audit names: Certora SR3, Statemind SR3 = 2026 Staking Router v3 audits. Certora V3, MixBytes V3, Consensys V3 (Consensys Diligence) = 2025 Lido V3 audits. Certora V3 fix review = 2026. Hexens V2, Certora V2, Statemind V2 = 2023 Lido V2 audits. Composable EDF, MixBytes EDF = 2026 EDF and DSM v5 audits. Ack3 NEST = 2026 Ack3 audit that covers `TokenRateNotifier`. Statemind TW = 2025 Triggerable Withdrawals audit.

Cross-cutting:

- **Privileged power** inside a role (Immunefi centralization and privileged-access exclusions). Still report if a non-holder gets the power, a holder exceeds a code-enforced bound, a check is missing, or an honest documented action causes loss through a defect.
- **Pauses.** Pausers can pause the section 3 pausables, and `ResealManager` can make a pause indefinite (LIP-34). Claims and unstETH transfers stay open. Still report if a non-holder pauses or resumes, a paused path moves value, or a pause causes permanent loss.
- **Empty revert data.** A rebase observer that reverts with empty data aborts the oracle report (Ack3 NEST, L6). A module hook (exit notification, rewards or exited-count report, credentials change) that does so reverts the call with `UnrecoverableModuleError` (`SRLib.sol`). Still report an unprivileged trigger, or a halt from a non-empty revert, other than the intended `DepositsPaused` status after a failed credentials-change hook.
- **Permissionless initializers and migrations** rely on atomic deployment (Hexens V2, LID-13). `migrateBaselineSnapshot` checks only empty history and `Lido` version 4. Still report if a third party can initialize, finalize or migrate a live contract or one the protocol reads.
- **Old OpenZeppelin 4 role storage** stays in `StakingRouter` (Statemind SR3, INFORMATIONAL-03). Still report code that reads it for authorization.
- **Rounding.** A 1 wei transfer can move 0 shares (Hexens V2, LID-25). With a share rate below 1, `transferSharesFrom` of a small share amount spends 0 allowance, so anyone can move another holder's shares (Certora V3, L-10). The mainnet rate is above 1. Claims leave 1-2 wei of dust. Still report rounding that is profitable, accumulates into a measurable loss, or breaks a solvency check.
- **Timestamps.** `ValidatorsExitBus._getTimestamp()` returns `uint32` and overflows in 2106 (Statemind SR3, INFORMATIONAL-44). Still report an earlier overflow.

Accounting and oracle:

- **Negative rebase fails closed:** a CL decrease above `maxCLBalanceDecreaseBP` over 36 days reverts the oracle report while no second-opinion oracle is set (LIP-23). Still report a permissionless trigger, or a window baseline that a non-oracle actor can steer.
- **Third-party deposits to Lido keys** raise the pending balance, tolerated up to `externalPendingBalanceCapEth` (Certora SR3, C-01, fixed with this slack). Still report growth above the cap that costs the attacker less than the cap.
- **Bad debt.** Smoothing ignores bad debt, and fees are computed before internalization (Certora V3, M-07, M-08, Certora SR3, L-03). `internalizeExternalBadDebt` can overstate the loss (MixBytes V3, M-1). Bunker mode starts only at the next oracle report, and vaults operate in bunker mode (MixBytes V3, H-1, M-3). Bad debt can be internalized while PDG compensation is available (Certora V3, M-10). Still report bad debt that a non-governance actor creates or times for profit, an error above that oracle report's bad debt, or bad debt in the share rate without `internalizeBadDebt`.
- **Staking limit.** `rebalanceExternalEtherToInternal` ignores the staking pause and limit (Certora V3, M-19). External burns can lift the current limit above its maximum (Statemind SR3, INFORMATIONAL-01, fix deferred to a core issue). A `setMaxExternalRatioBP` update can be front-run (MixBytes V3, L-1). Still report supply growth without ETH, or `mintExternalShares` above the limit.
- **Smoothing** is malleable by same-block `submit` (Certora SR3, L-06). Still report a sandwich that is profitable at mainnet stake with mainnet limits (section 7, parameters).
- **EL rewards.** `Lido` ignores the `withdrawRewards` return value (MixBytes V3, L-11, Statemind SR3, INFORMATIONAL-43). Still report a withdrawn amount that differs from the checked amount.
- **Share-rate reconstruction** omits fee-share divergence (Statemind SR3, INFORMATIONAL-22). Still report finalization above the true rate by more than the configured deviation.
- **Deposits reserve** limits only deposits and top-ups on-chain. Keeping finalization out of it is an off-chain oracle rule (LIP-35). Still report an on-chain consequence.

Deposits:

- **Trusted modules.** A malicious module can steal deposits, falsify counts or revert all deposits (Statemind V2, CRITICAL-02). A node operator can circumvent DAO validator key approval (Statemind V2, HIGH-07). Still report an unprivileged actor that makes an honest module misbehave, or a change to another operator's keys.
- **Deposit liveness.** An operator can bump its module nonce, and anyone can change the deposit root (Statemind V2, MEDIUM-16, Certora V2, H-01). A withdrawal request can revert a near-maximum deposit or top-up (Certora SR3, L-04). Still report a grief that needs neither, outlasts the attacker's spending, or blocks calls far below the depositable budget.
- **DSM rules.** The quorum may exceed the guardian count (DSM NatSpec). An unexpired pause signature works again after an unpause (Composable EDF, LDO-55729910-L04). Admission checks only ERC-165 support for ERC-1271, the ECDSA path stays, and terminated delegation contracts stay (MixBytes EDF, L-1, L-3). A future-block pause intent reverts (Statemind SR3, INFORMATIONAL-17). Still report a seed deposit with fewer than `quorum` valid signatures, a signature valid for a non-guardian or another seat, a seat counted twice, a message accepted as another type, or a replay after the intent window.
- **Top-ups and consolidations.** Top-ups rely on `TOP_UP_ROLE` and proofs instead of the guardian quorum (LIP-35). The gateway proves only the consolidation target, and the consensus layer enforces the source because `WithdrawalVault` is the request source (LIP-35). Consolidations ignore the "quorum above guardian count" stop and module status (Certora SR3, I-02, Statemind SR3, INFORMATIONAL-31). Still report ETH or stake on a validator without Lido `0x02` credentials, a top-up or consolidation past the section 3 bound of its role, excess above MaxEB that cannot return to Lido, or a consolidation while DSM deposits are paused, `Lido` is stopped, or bunker mode is active.
- **Rate limits.** The bus delay is global and unbounded, a reset drops accrued capacity, and the two rate-limit libraries differ (Statemind SR3, INFORMATIONAL-30, INFORMATIONAL-32, Certora SR3, I-04). Still report any caller above a configured rate or before the delay.

Withdrawals and exits:

- **Oracle batches.** Mixed batches can lock more ETH than claims need (Certora V2, H-05). One finalization gives partial rate recovery (Certora V2, M-04). Still report claims above locked ETH, an over-lock forced by a non-oracle actor, or a payout above nominal stETH.
- **Claim to `Lido`** mints stETH to the queue (Hexens V2, LID-19). Still report a non-owner that picks the recipient.
- **Permit front-run** reverts `requestWithdrawalsWithPermit` (`lidofinance/core` issue #803). Still report more than a revert.
- **Exit re-trigger.** Anyone can re-trigger delivered exit data and drain the gateway quota (LIP-30 section 6.2, Statemind TW, MEDIUM-01, Certora SR3, L-01). Still report a trigger without the full fee, above the limit, or for undelivered data.
- **Exit-bus paths.** `maxValidatorsPerReport` and the exit bucket apply only to the hash path (Statemind SR3, INFORMATIONAL-39). The hash path may use data format 1 (LIP-35). Undelivered pre-upgrade hashes stay stuck (Statemind SR3, INFORMATIONAL-38). Still report a VEBO report above `maxBalanceExitRequestedPerReportInEth` or without the key check, or unverified data delivered without a role-committed hash.

stVaults:

- **Operator powers.** The operator's depositor can move a vault's available ETH into that vault's validators, and the operator manager can make unguaranteed deposits (`Dashboard.unguaranteedDepositToBeaconChain`, `NODE_OPERATOR_UNGUARANTEED_DEPOSIT_ROLE`) after the owner opts in (Lido stVaults documentation). The 1 ETH predeposit to a not-yet-proven pubkey is the designed first stage, covered by the node operator's bond. Still report an activation or a later deposit with other credentials or to an unproven pubkey, a predeposit that the bond does not cover, a deposit from another validator's staged ETH, or a deposit without the role.
- **Ownership and incentives.** Vault ownership transfer outside the Dashboard skips node-operator approval (Consensys V3, 7.22). Slashing cost falls fully on node operators, and rebalancing and forced exits pay no incentive (Consensys V3, 7.25, 7.28). Still report a transfer by a non-owner, or a change of tier, limits or fees without both confirmations.
- **Quarantine** holds the whole increase, not only the excess (Certora V3, L-05). PDG compensation bypasses `inOutDelta` and can trigger quarantine (Certora V3, L-21). Still report early release, double counting, or quarantined value in minting capacity.
- **Self-rebalance rounding.** Repeated small rebalances can make the owner's own vault unhealthy (Certora V3, L-19). Still report loss that reaches stETH holders, the node operator or other vaults.
- **Lifecycle.** Reconnect resets the tier (Certora V3, L-08). Forced disconnect skips operator fees (Certora V3, L-17, Consensys V3, 7.13). Confirmations survive until expiry (Consensys V3, 7.27). Still report better terms after reconnect, cleared jail, dropped liabilities, or a confirmation reused for other calldata or another confirmer.
- **Jailed owner** can delay `forceValidatorExit` with a deposit that `forceRebalance` consumes (Certora V3 fix review, I-01). Still report a free or third-party block, or a partial withdrawal from a jailed vault.
- **One vault report** can revert for about a day after an out-of-order vault report with gifts (Certora V3, L-11). Still report a third-party block longer than one frame, or of all vaults.

## 7. How we rate severity

Severity follows the worst consequence the same root cause reaches on mainnet. The parameters in `/src/deployed-mainnet.json` (`constructorArgs` and each contract's `deployParameters`) are the mainnet values at deployment. Where a value is settable by governance, any value the setter accepts is possible, and the report should name the setter and the value, because Lido checks the live value at triage.

| Level         | Impact                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Critical      | An unprivileged actor steals ETH, stETH, wstETH, claimable unstETH ETH, stVault ETH or PDG bonds. Unbacked stETH: shares without ETH, external stETH beyond vault collateral with honest oracle data, or a share-rate drop outside an oracle report. Buffered ETH, a top-up, a PDG deposit or consolidated stake reaches a validator without Lido (or the vault's) credentials. Claims above entitlement. Permanent freeze of user funds. Dual Governance veto or rage-quit weight changed without locking the matching value.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| High          | Theft or permanent freeze of yield (protocol fees, module rewards, EL rewards, vault Lido fees, stVault node-operator fees). Treasury loss. A role, proxy admin, vault ownership or guardian seat without a grant. A role-gated or caller-pinned change without the role. A change of another party's vault tier, share limit, fee rate or settled growth without both confirmations. A bypass of the DSM quorum, pause or signature domain on the seed-deposit path. An exit without a delivered request, above a configured limit, or without the full fee. A false exit-delay proof accepted. Reversible freeze: an unprivileged actor blocks claims, finalization, every oracle report, or vault withdrawals until governance or a role holder acts. A profitable attack on the share rate or rebase. A share-rate change outside an oracle report, beyond the rounding of `submit` and small transfers, that extracts value, breaks backing, or changes a liability or Dual Governance weight through `getPooledEthByShares`, `getSharesByPooledEth`, `stEthPerToken` or `tokensPerStEth`. Repeatable Lido-fee avoidance by a vault owner. |
| Medium        | Griefing without profit: a revert of one oracle report or VEBO report that ends without governance action. A halt of seed deposits, top-ups or consolidations that is new, cheaper or longer than the accepted cases in section 6. A bounded delay of one vault's report, rebalance or forced exit. Harmful front-running. Block stuffing for profit.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Low           | Promised returns not delivered, no value lost. Wrong views or events that no core contract, wstETH integration, token-rate push or Dual Governance escrow uses for value. Over-deposit above MaxEB that the consensus layer returns to Lido credentials.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Informational | Best practice, gas, style, unreachable branches, a few wei of rounding without profitable repetition, and re-entrancy or off-chain effects with no on-chain impact. Not worth a report.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

Adjustments specific to this protocol:

- A bounded or trusted actor of section 3 acting inside its bound is not a vulnerability. A bounded actor that passes a check it should fail is a finding, rated by the excess.
- A value that core accepts from governance or Easy Track is configuration. A core invariant that breaks for some accepted value is a finding; the setter and the value matter.
- Leaked keys, social engineering, 51% attacks and governance capture are out of scope.
- Self-harm is Informational only when the whole loss stays with the actor. An action on the actor's own vault, validator or position that moves loss to stETH holders, the vault's node operator, PDG guarantors or other vaults is not self-harm (Certora V3, C-03, H-03).
- A deposit halt alone does not freeze user funds, because finalization uses the buffer without the deposit path.
- A freeze that no role action in the current code can end is permanent, even if a proxy upgrade or redeploy can end it. Dashboard code cannot be upgraded for existing vaults, and ossified vaults keep their implementation.
- A "Live, unused path" or "Future upgrade" finding is rated by its impact once the path is reachable; what makes it reachable (a fork that changes `BeaconState`, a redeploy, a migration) is part of the finding. "Not deployed / retired" code matters only where a live contract is affected.
- The amount at risk is the total the same root cause can reach on mainnet (every vault, every request, the whole buffer), in ETH and shares. Lido does not rate by USD.
- `StakingRouter`, the consolidation bus and migrator, and `NodeOperatorsRegistry` have no pause. The pausables and their pausers are in section 3.

- Chain time comes from `getCurrentBlockTimestamp()` in `lib` or `time.latest()`, not from the wall clock.
- A Solidity helper belongs in `test/poc/contracts/` with `pragma solidity 0.8.25`. `SKIP_INTERFACES_CHECK=true SKIP_LINT_SOLIDITY=true yarn hardhat compile` compiles it in about 40 s; tests then run with `--no-compile`.
- The Hardhat network uses Prague, a 30M block gas limit and `allowUnlimitedContractSize: true`, so bytecode size is not checked there. The EIP-4788 contract exists. `lib/eips/` injects the EIP-7002 and EIP-7251 predeploys.
- For a proof, `prepareLocalMerkleTree` (`lib/pdg.ts` for PDG and consolidation, `lib/top-ups.ts` for top-ups) builds an honest tree. `updateBeaconBlockRoot` (`lib/eips/eip4788.ts`) writes any root, so a reproduction with a fabricated root proves nothing.

## 9. How we would like reports and patches to look

One root cause is one finding. A defect in shared code (`SSZ`, `GIndex`, `BLS`, `CLProofVerifier`, `WithdrawalCredentials`, `RateLimit`, `PausableUntil`) is one finding that lists every affected contract. The two `PausableUntil` files (`contracts/common/utils/PausableUntil.sol`, `contracts/0.8.9/utils/PausableUntil.sol`) are copies: a defect present in both is one finding that names both. Several defects that combine into one attack are one finding that explains each defect.

What Lido needs in a report: the deployment status of section 1 and the commit the code was read at; the affected contracts and their `deployed-mainnet.json` keys; the bounded or trusted actors the attack needs, and any behaviour of an external system it relies on; the section 4 invariant or the code-enforced bound that fails; the reproduction, run against unmodified `contracts/`, or the exact code path with the steps that were not reproduced; the state before and after (balances, shares, locked ETH, liabilities) and the amount at risk on mainnet; which pause, guardian or governance action stops the attack and how fast; and, for a variant of a section 6 item, what is new. Severity is about impact; confidence is separate, so a finding reasoned from code without a reproduction keeps its level and says so.

Patches:

- Keep the patch minimal and add a regression test to the subsystem's test file. Use the solc version of the contract's folder. For `contracts/common/`, keep the pragma range and make the change compile under every importing solc version (0.4.24 for imports from `Lido`, `StETH`, `StETHPermit` and `NodeOperatorsRegistry`).
- Keep the storage layout of every proxied contract and check it per contract. `StETH`, `ConsolidationBus`, `ConsolidationMigrator` and the Dashboard clones use sequential slots (append only). `Lido` and most 0.8.9 contracts use unstructured positions. `Burner`, `StakingRouter` (`SRStorage`), `TopUpGateway` and the stVault core contracts (`VaultHub`, `LazyOracle`, `OperatorGrid`, `PredepositGuarantee`, `StakingVault`) use ERC-7201 namespaces.
- `Lido`, `NodeOperatorsRegistry` and Simple DVT are Aragon `AppProxy` instances that the Kernel upgrades. Each `StakingVault` upgrades through the beacon, except vaults whose owner ossified them. Each Dashboard is a non-upgradeable ERC-1167 clone with immutable arguments, so a Dashboard fix reaches only new vaults.
- Non-proxy contracts (`DepositSecurityModule`, `OracleReportSanityChecker`, `HashConsensus`, `TriggerableWithdrawalsGateway`, `ConsolidationGateway`, `ValidatorExitDelayVerifier`, `TokenRateNotifier`, `LidoExecutionLayerRewardsVault`, `WstETH`, `VaultFactory`, `OracleDaemonConfig`, `EIP712StETH`, `ValidatorConsolidationRequests`): a fix needs a redeploy, a new `LidoLocator` implementation where the locator lists the contract, and role moves. `WithdrawalVault` caches both gateway addresses as immutables, so a gateway redeploy also needs a vault upgrade.
- `SRLib`, `BeaconChainDepositor` and `MinFirstAllocationStrategy` are linked libraries. A fix there needs a new `StakingRouter` implementation. A fix in `MinFirstAllocationStrategy` also needs a new `NodeOperatorsRegistry` implementation (NOR and Simple DVT).
- `VaultHub` compiles with optimizer runs 100 to fit the size limit, and the image sets `SKIP_CONTRACT_SIZE=1`, so its bytecode size needs a separate check after a patch.
- `yarn hardhat compile` without the skip flags runs the `lint-solidity` and `check-interfaces` tasks that CI requires.
